## 미공개

### 원격 액세스

- **공유가 재시작 후에도 유지됩니다.** 지금까지는 서버가 시작될 때마다 페어링 토큰이 새로 생성되어, VelaTerm을 종료했다가 다시 열면 공유한 링크가 모두 조용히 무효화되고 모든 기기를 다시 페어링해야 했습니다. 이제 토큰, 페어링된 기기, 기기 차단 목록이 데이터 디렉터리의 소유자 전용 파일에 저장됩니다. 이미 페어링된 기기는 재시작 후에도 저장된 URL로 다시 연결되며(액세스 비밀번호는 여전히 필수 2차 인증 요소입니다), 차단된 기기는 계속 차단된 상태로 남습니다. 또한 VelaTerm은 공유가 켜져 있었다는 사실을 기억합니다. 서버가 실행 중인 상태로 앱을 종료하면 다음 실행 시 같은 포트에서 자동으로 다시 시작됩니다 — 데스크톱 앱에서든 `--serve`로 동작하는 GUI 없는 서버에서든 동일합니다. 직접 중지한 경우에는 아무것도 자동으로 시작되지 않습니다. 포트가 사용 중인 경우처럼 자동 시작이 실패해도 앱은 정상적으로 실행되며 원격 액세스 패널에 원인이 표시됩니다. 포트 입력란은 기본값으로 되돌아가지 않고 실제로 사용한 포트를 기억합니다. "링크 재생성"은 여전히 명시적인 무효화 수단입니다. 즉시 새 토큰을 발급하고 기존 링크를 모두 무효화하며 저장된 상태를 덮어씁니다. 액세스 비밀번호 자체는 절대 디스크에 기록되지 않으며, 저장되는 것은 메모리 하드 해시(Argon2id)뿐입니다.

### 원격 접속

- **공유 링크가 사용할 주소를 선택할 수 있고, Tailscale 주소도 이제 표시됩니다.** 주소 목록이 기존의 사설 IPv4 대역만 허용했기 때문에, 캐리어급 NAT 대역(100.64.0.0/10)의 주소를 할당하는 Tailscale 같은 VPN 메시는 서버가 이미 그 경로로 접근 가능했음에도 원격 접속 패널과 페어링 링크에서 조용히 제외되었습니다. 이제 이 주소들이 목록에 표시되며, VPN 터널은 기본값이 되지 않도록 맨 뒤에 배치됩니다. 패널에 추가된 IP 선택기(시작 전과 실행 중 모두 표시)는 각 후보를 인터페이스 이름과 함께 보여 주고 VPN 터널을 표시합니다. 주소를 선택하면 해당 URL이 맨 앞으로 이동하고 페어링 링크가 정확히 그 호스트로 다시 생성되므로, 복사한 링크는 VPN을 통해서만 이 컴퓨터에 도달할 수 있는 기기에서도 URL을 손으로 수정하지 않고 그대로 동작합니다. 페어링 링크 아래의 QR 코드는 휴대폰으로 바로 스캔할 수 있습니다. 선택은 기억되며, 선택한 인터페이스가 사라지면 선택을 잊지 않은 채 ‘자동’으로 되돌아갑니다. 서버 자체는 변경되지 않았고 계속 모든 인터페이스에서 수신 대기합니다. 서버 시작 후에야 나타난 주소(예: 나중에 연결된 VPN)를 선택하면 이제 페어링 링크뿐 아니라 복사되는 URL과 QR 코드도 즉시 갱신됩니다(예전에는 다음 재시작까지 페어링 링크만 따라갔습니다). VPN 터널은 모든 플랫폼에서 LAN 주소 뒤에 정렬되고, 서버가 중지된 상태에서 고른 주소는 시작 후 첫 페어링 링크에 사용되며, 겹치는 링크 재생성이 더 새로운 링크를 더 오래된 링크로 덮어쓰는 일도 없어졌습니다.

### 보안

- **페어링된 기기가 더 이상 공유 자체를 관리할 수 없습니다.** 지금까지는 페어링된 브라우저가 데스크톱 앱과 동일한 관리 명령을 호출할 수 있었습니다 — 새 페어링 링크 생성(기기 차단 목록도 함께 비워집니다), 다른 기기 목록 조회와 해지, 서버 중지와 재구성까지. 또한 설정 저장소는 접근 비밀번호의 메모리 하드 해시와 다음 실행이 읽는 자동 시작 설정을 포함한 전체 설정을 모든 클라이언트에 넘겨주었습니다. 이제 관리 명령은 데스크톱 앱과 Electron 셸 전용이며, 설정 API는 페어링된 기기의 읽기에서 원격 접속 키와 Gitea 토큰을 걸러내고 해당 키에 대한 쓰기를 거부합니다. 페어링된 기기는 페어링의 본래 목적 — 터미널 세션과 완전한 셸 접근 — 은 그대로 유지하지만, 비밀번호 검증값을 읽거나 다른 기기를 초대·추방하거나 다음 시작이 사용할 포트를 바꿀 수는 없습니다. 저장된 비밀 정보를 읽거나 쓰거나 삭제하는 명령 — Gitea 토큰과 기억된 호스트 비밀번호 — 도 이제 페어링된 기기에서는 거부되며, 경로를 받는 명령 — 읽기, 미리보기, 쓰기, 생성, 이름 바꾸기, 삭제는 물론 파일의 git diff 표시와 저장소를 복제할 폴더 선택까지 — 은 심볼릭 링크를 먼저 해석한 뒤 페어링 상태와 키가 보관된 VelaTerm 자체 데이터 디렉터리 내부 경로를 거부합니다. 그 외의 모든 경로는 그대로 동작하므로 원격 파일 탐색과 편집은 계속 사용할 수 있습니다. 경로를 받는 모든 원격 명령을 테스트가 열거하므로, 새 명령이 이 검사를 몰래 지나칠 수 없습니다. 이러한 보호 장치가 요청을 거부하면 브라우저에는 이제 영어 원문 오류 대신 제대로 번역된 메시지가 표시됩니다.

- **해지나 링크 재생성이 이중 인스턴스 구성에서도 유지됩니다.** 자동 시작을 켠 헤드리스 `--serve` 서버에서는 두 서버 인스턴스가 각자 저장된 페어링 상태 사본을 들고 전체를 다시 써서, 한쪽에서 수행한 해지나 새 페어링 링크가 다른 쪽에 의해 조용히 되돌려질 수 있었습니다. 이제 한 프로세스의 모든 인스턴스는 데이터 디렉터리별로 단일 페어링 상태를 공유합니다. 해지와 회전은 즉시 모든 곳에 적용되고, 파일 기록은 정확히 한 곳으로 모입니다. 파일은 실제 재시작을 넘어 유효한 원본으로 남습니다.

- **반복된 로그인 실패는 제한됩니다.** 접근 비밀번호 검증은 의도적으로 비용이 큰 Argon2id를 사용하며, 포트에 도달할 수 있는 누구나 시도할 수 있습니다. 같은 주소에서 다섯 번 실패하면 이후 시도는 해시 작업이 시작되기 전에 1분 동안 거부됩니다. 해시 계산 자체도 이제 서버의 이벤트 루프 밖에서 실행되며 동시 검증 수에 엄격한 상한이 있습니다. 잘못된 비밀번호를 쏟아부어도 서버를 메모리 하드 해시로 포화시키거나 이미 연결된 기기의 응답을 늦출 수 없습니다. 이 제한은 메모리에만 존재하며 서버 재시작으로 초기화됩니다. 실제 방벽은 여전히 페어링 토큰과 비밀번호입니다. 이 제한은 이제 같은 데이터 디렉터리를 사용하는 모든 서버 인스턴스가 공유하므로 `--serve` 이중 인스턴스 구성에서도 시도 예산이 두 배가 되지 않으며, 비밀번호 검증이 시작되기 전에 시도가 예약되므로 한 주소에서 오는 병렬 요청이 제한을 빠져나갈 수 없습니다. 제한된 브라우저에는 이제 비밀번호가 틀렸다는 안내 대신 로그인 화면에 전용 속도 제한 메시지가 표시됩니다. 또한 속도 제한은 더 이상 틀린 비밀번호처럼 기억되지 않습니다. 대기 시간이 지나면 페이지를 새로 고치지 않아도 다음 시도가 다시 처리됩니다. 중간에 중단된 시도(비밀번호 검증 중에 탭이 닫힌 경우)는 이제 남은 1분 동안 해당 주소에 계속 집계되는 대신 예약된 자리를 즉시 해제합니다. 또한 로그인에 성공해도 자신의 예약만 해제될 뿐 해당 주소의 기록 전체가 지워지지는 않습니다. 공유 네트워크 주소 뒤에서는 누군가 올바르게 로그인해도 공격자의 시도 예산이 초기화되지 않으며, 기록된 실패는 해당 1분이 지나야만 만료됩니다.

- **디스크와 로그의 비밀 정보를 더 신중하게 다룹니다.** 페어링 상태 파일과 종단 간 암호화 키는 첫 기록 후에 제한하는 대신 생성 시점부터 소유자만 읽을 수 있게 만들어지고, 비밀번호 해시가 담긴 세션 데이터베이스도 소유자로 제한됩니다. 헤드리스 `--serve`는 페어링 링크의 수명이 긴 비밀을 더 이상 로그에 출력하지 않습니다. 출력이 터미널이 아니면 링크를 감추고 안내만 표시하며, `--print-pairing`으로 명시적으로 되돌릴 수 있습니다. 기기 레지스트리는 이름 길이를 제한한 32개 항목으로 상한이 정해져 페어링된 클라이언트가 저장 파일을 무한정 키울 수 없고, 해지나 새 페어링 링크 저장이 실패하면 그 오류가 로그 한 줄이 아니라 호출자에게 전달됩니다. 자동 시작은 이미 수동으로 시작된 서버를 더 이상 대체하지 않으며, 오래된 자동 시작 오류는 서버를 직접 중지하면 사라집니다.

### 수정

- **Electron 셸에서도 페어링을 관리할 수 있게 되었습니다.** 페어링 링크 생성, 페어링된 기기 목록 조회, 기기 해지는 데스크톱(Tauri) 명령으로만 존재했고, Electron 셸과 브라우저 클라이언트가 사용하는 WebSocket 디스패처는 "Unknown command"를 반환해 원격 접속 패널이 그곳에서는 동작하지 않았습니다. 이제 세 명령 모두 두 전송 방식에서 동일한 코어 함수를 거치므로 서로 어긋날 수 없으며, 실행 중인 로컬 서버를 상대로 실제 페어링 링크를 생성하는 테스트를 포함한 회귀 테스트가 새 디스패치 경로를 검증합니다.

### AI 에이전트

- **Kiro CLI가 일급 세션 유형으로 합류했습니다.** Kiro 세션은 트리에서 자기 노드를 가지며, Kiro 자체 lifecycle hooks가 작업 중·대기 중 상태 표시등을 정확하게 몰아줍니다. 턴이 끝나면 알림이 오고, 노드를 다시 열면 같은 대화가 자동으로 이어지며, 실행 인자와 확인 건너뛰기 전환, vspawn을 통한 실행까지 다른 에이전트가 이미 갖고 있던 기능을 그대로 제공합니다. VelaTerm은 기본 Kiro 에이전트를 자체 `vlx-term` 에이전트로 복제하고, 복사본에만 관찰 전용 lifecycle hooks를 추가한 뒤 그것을 실행합니다. 사용자의 에이전트 파일은 전혀 수정되지 않으며 프롬프트, 도구와 MCP 서버는 그대로 따라옵니다. Kiro에는 권한 요청 hook이 없으므로 승인을 기다리는 동안에는 표시등이 작업 중으로 남습니다.

### 수정

- **터미널에서 시작한 프로그램이 더 이상 AppImage 자체 환경을 물려받지 않습니다(Linux).** AppImage 실행기는 `PYTHONHOME`, `PYTHONPATH`, `PERLLIB`, `QT_PLUGIN_PATH`와 GStreamer 플러그인 경로를 번들의 임시 마운트 디렉터리로 지정하고, `PATH`와 `LD_LIBRARY_PATH`의 맨 앞에 번들 디렉터리를 넣습니다. 터미널은 자신의 환경 전체를 시작하는 shell에 넘기므로, 시스템 `python3`가 표준 라이브러리를 번들 안에서 찾다가 아예 실행되지 못했고, 동적 링크된 다른 프로그램도 시스템 라이브러리 대신 번들에 든 사본을 먼저 불러왔습니다. 이제 VelaTerm은 shell이나 외부 도구를 시작하기 전에 이런 번들 경로를 제거하며, 사용자가 직접 설정한 값은 건드리지 않습니다. `APPDIR`와 `APPIMAGE`는 그대로 남으므로 AppImage에서 실행 중인지 확인하는 프로그램은 여전히 답을 얻습니다. AppImage 빌드만 영향을 받았고 deb 패키지, macOS와 Windows는 이전과 동일합니다.

### 터미널

- **Shift+Enter가 전송 대신 줄바꿈을 입력합니다.** 터미널에는 수식 키를 포함한 Enter를 나타내는 인코딩이 없어서 Claude Code, Codex 같은 에이전트 CLI에는 일반 캐리지 리턴만 전달되었고, 입력을 마치기도 전에 프롬프트가 전송되었습니다. 이제 VelaTerm은 ESC+CR을 보냅니다. 해당 도구들이 iTerm2 키 매핑에서 기대하는 것과 같은 시퀀스이므로 여러 줄 입력이 가능해졌습니다. 그동안 사용자 지정 키 핸들러가 아예 설치되지 않았던 macOS도 포함됩니다. 입력기 조합 중에는 동작이 바뀌지 않으므로 Enter로 후보 단어를 계속 확정할 수 있습니다.
